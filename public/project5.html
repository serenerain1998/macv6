The Problem

Clinical environments aren't short on technology. They're short on attention.

Multiple roles, overlapping workflows, dozens of disconnected systems. Every screen demands a hand. Every alert demands a glance. Cognitive load is the real bottleneck — not data, not capability.

Switching between tools mid-care is dangerous. Looking down at a tablet during a critical moment is dangerous. The interface itself becomes a source of risk. The work happens with hands and eyes elsewhere, but most software is still built for screens you stop and stare at.

My Approach

I started with workflows, not screens — designing around the people involved and the moments that matter

Step 1: Map Where Attention Breaks

Before designing anything, I mapped the moments where attention shifts away from the patient — handoffs, verifications, retrieval, documentation. These are the seams in the workflow where friction accumulates and where an ambient layer could quietly absorb the load.

  • Identified attention-break points across a typical care workflow
  • Categorized moments by cognitive cost and frequency
  • Looked for tasks that didn't require hands or eyes
  • Marked which moments belonged to which role

Step 2: Design Around Roles, Not Data

Different roles need different things from the same moment. The system has to know whose voice it's hearing and what stage of the workflow they're in. I modeled the same interaction from multiple perspectives — what's useful to one role is noise to another.

  • Defined role-specific signal vs. noise for each workflow stage
  • Mapped when a role wants confirmation vs. quiet acknowledgment
  • Designed shared moments where multiple roles overhear the same response
  • Built voice-recognition into the interaction model from the start

Step 3: Model the Interaction Patterns

I didn't model commands. I modeled patterns. When the system stays silent. When it speaks. When it surfaces something visually. When it gets out of the way entirely. This is where the design lives — in the rhythm and timing, not the words.

  • Defined four response modes: silent, audible, visual, and deferred
  • Built decision rules for which mode fits which moment
  • Designed for graceful failure — when in doubt, the system stays quiet
  • Specified short-form responses by default (one sentence or none)

Step 4: Prototype Behavior, Not Screens

You can't validate ambient design by reviewing mockups. I prototyped the actual behavior — voice scripts, timed scenarios, role-based interaction flows. The point wasn't how it looked. It was how it felt in the room.

  • Wrote conversational scripts for high-friction moments
  • Walked through timed scenarios with multiple speakers
  • Tested when silence was the better answer
  • Iterated on response length, tone, and timing

Design Principles

Five rules that shaped every decision — when to speak, when to listen, and when to disappear

Restraint as a Feature

Every principle pulls in the same direction: the system earns attention by not demanding it. These aren't aspirations — they're decision criteria.

  • Passive until needed. Listening, not interrupting.
  • Context-aware. Knows the role, the workflow, the moment.
  • Minimal responses. Says only what's useful. Never more.
  • Non-intrusive. No alert that doesn't earn its place.
  • Trust-driven. The clinician stays in control. Always.

Interaction Model

Voice-first, workflow-aware, and visually quiet — the model coordinates input, response, and silence

Voice First, Visual Second

Voice is the primary input — short phrases, natural language, no clumsy wake words to fumble in a critical moment. Responses are short. Often one sentence. Sometimes none at all.

  • Natural activation. Recognizes intent without rigid command syntax.
  • Workflow-aware behavior. Reads the stage, knows when a question is rhetorical.
  • Coordinated UI. Visual updates appear on peripheral displays only when they add value.
  • Silence as a response. When nothing useful can be said, the system says nothing.

AI as Interface Controller

The assistant doesn't just talk — it acts. Voice or text commands can drive the UI itself.

Conversation Becomes Action

Most AI assistants are bolted on top of an interface — they answer questions but can't reach into the UI. This system can. A spoken phrase or typed prompt isn't just a query; it's a command the system can execute against the live interface.

  • Voice and text parity. Same intent surface — say it or type it, the system responds the same way.
  • UI-aware actions. Open a panel, surface a record, filter a list, switch context — all triggered by natural language.
  • Contextual continuity. The assistant tracks workflow state, so commands like "show me the last one" or "go back" resolve correctly without restating context.
  • No menus to learn. Anything reachable through clicks is reachable through conversation. The interface stops being a maze.

Prototyping

You can't validate ambient design by reviewing mockups — you have to hear it

Behavior Over Pixels

Static screens couldn't tell this story. I prototyped the actual behavior — the timing, the silence, the moments the system speaks and the moments it doesn't.

  • Voice scripts. Written exchanges for high-friction moments, tuned for length and tone.
  • Scenario walkthroughs. Timed dialogues with multiple roles in a single space.
  • Interaction flows. Branching maps of when the system speaks, surfaces, or stays quiet.
  • Felt experience. The point wasn't how it looks. It was how it feels in the room.

See It In Action

Six short clips, each one a real interaction — from waking the assistant to controlling consoles by voice

Wake & Greet

The assistant lives in a sleep state until I speak to it. The first interaction matters — I greet it, and it greets me back by name.

  • Sleep to awake. A natural greeting wakes the system; no button press, no wake word.
  • Personal recognition. The assistant knows who's in the room and responds accordingly.
  • Tone-setting. Being known immediately changes how the rest of the conversation feels.

Case Count for the Day

I ask how many cases I have today. The assistant pulls from my schedule, recognizes the role, and answers immediately — no menu, no app switch.

  • Schedule-aware. The system has my day already loaded and contextual.
  • Personalized. Knows whose schedule it's referencing without me specifying.
  • Single-step answer. One question, one response — no drilling through views.

Hands-Free UI Updates

In a sterile environment, every touch is a tradeoff. I voice-prompt the assistant to update the case counts, and it modifies the UI on my behalf — no gloves coming off, no second device, no break in workflow.

  • Voice as a hand replacement. Exactly when touch isn't an option.
  • UI updates from natural language. The system reaches into the interface and acts.
  • Sterile-field-safe. No need to step away from the case to log something.

Surgeon Preference Cards on Demand

The scrub tech needs to know exactly how this surgeon prefers their tools laid out. I ask for the prep cards for the procedure, and the assistant pulls them up in a lightbox — zoomable and navigable entirely by voice.

  • Procedure-specific. The right cards for the right surgeon, surfaced by name.
  • Voice-controlled lightbox. Zoom in, zoom out, next image — all spoken.
  • Reference without contact. Sterility preserved; no surface touched.

The Schedule, Conversationally

I ask the assistant to show me the schedule. From there it's a conversation — filter by surgeon, open a specific day, ask what cases a provider has, all by voice. The interface bends to questions instead of the other way around.

  • Voice-driven filtering. Narrow down by surgeon, date, or procedure type without clicking.
  • Drill into a day. Open the details for any date and walk through what's scheduled.
  • Conversational follow-ups. "What does Dr. X have tomorrow?" works as a natural next question.

Console Telemetry & 3D Inspection

Fluid system, shaver, camera system, RF — every console has its own stats and state. The assistant gives me the rundown on demand. There's also an interactive 3D model rendered with three.js that rotates a full 360° for inspection.

  • Live stats by voice. Fluid, shaver, camera, RF — pulled in real time.
  • Per-console drilldown. Ask about one system, get the metrics that matter for it.
  • Interactive 3D model. Built with three.js — orbit and inspect the equipment from any angle.

Anthropic Claude — The Conversational Brain

Claude handles the natural language layer — interpreting intent, holding context across the workflow, and responding in short, human phrasing rather than rigid command output. Haiku 4.5 specifically gave me sub-second response generation, which is what makes a voice exchange feel like a conversation instead of a query.

OpenAI API — A Second Brain for Comparison

I tested the same workflows against OpenAI to compare tone, latency, and instruction-following. Different models have different conversational personalities — finding the right fit for a clinical context meant evaluating both.

ElevenLabs — Naturalistic Voice Output

The eleven_v3 model produces speech with the kind of pacing and emotional shading that mid-tier TTS can't match. For an ambient assistant, where the voice is the whole interface, this was non-negotiable. Streamed audio arrives as bytes, played progressively in the browser instead of waiting for the full file.

Web Speech API — Native, No Wake Word

Voice input runs directly through the browser's speech recognition — no native app, no wake word, no setup. Pressing the mic starts listening; the system handles the rest. It's the fastest way to a working ambient prototype without getting stuck in platform-specific tooling.

Streaming Architecture — Speak While Generating

The chat response streams from Claude word-by-word. As soon as a complete sentence is ready, it's dispatched to TTS — which itself streams audio bytes as they're synthesized. The next sentence pre-buffers while the current one plays. End-to-end perceived latency from "speak" to "hear" lands in the 1–1.5s range, which is the threshold for conversational comfort.

Reflection

The Hardest Part

It wasn't the AI. It was the restraint. Designing a system that knows when not to act is harder than designing one that responds to every input — but in environments like this, every unnecessary intervention is a distraction, and every distraction has a cost.

Where AI Is Heading

Not chatbots layered on top of dashboards. Ambient systems that understand context, respect attention, and earn trust by staying quiet until they have something worth saying. That's the bar.

Future Potential

The same pattern translates anywhere attention is finite and stakes are high — operating environments, emergency response, command centers. The technical foundations are here. What's missing is the design discipline to use them well.
